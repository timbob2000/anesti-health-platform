# Workspace application instructions

- Work from the configured application root. Use Node.js 22+. Install with `npm ci`, develop with `npm run dev`, build with `npm run build`, start with `npm start`, and verify with `npm test`. The HTTP port is 3000; readiness is `/health/ready`.
- Inspect `server/app.mjs`, `server/config.mjs`, `schema/onyx.schema.json`, and the README before changing data access. `client/` is browser code; Onyx and Firebase Admin remain exclusively under `server/`/migration scripts.
- Use the installed `@onyx.dev/onyx-database` SDK's real methods: `onyx.init`, `from().where(eq()).list`, `save`, `findById`, `delete`, `getSchema`, `diffSchema`, `validateSchema`, and `updateSchema`. Do not invent SQL, REST endpoints, provisioning APIs, or transaction support.
- Verify Firebase ID tokens on the server. Enforce ownership/authorization using the verified UID for every read/write; never trust a submitted owner ID. Preserve generic provider errors and log only request IDs/status. Do not log, read into prompts, commit, bundle, or print privileged credentials. `ONYX_DEBUG` must remain off.
- Keep light and dark themes, accessible labels, visible error/empty/loading behavior, mobile layout, and safe text rendering. Avoid inserting user content as HTML.
- Schema uses `entities`, case-sensitive Onyx attribute types, identifiers, indexes, and `isNullable`. Append an immutable numbered JSON migration alongside every change to the current schema. Preserve unrelated database tables. Run `npm run schema:diff` and `npm run schema:validate` with the designated environment's injected schema credentials before `npm run schema:publish` / `npm run migrate`.
- Migrations require a shared persistent `MIGRATION_STATE_DIR` across ALL runners for a database. Do not bypass locks, edit applied checksums, silently retry an uncertain write, or make a local directory look like a distributed lock. Use `npm run migrate:status` to inspect state. Inspect partial effects before `npm run migrate -- --retry=ID`.
- Destructive production actions need an explicitly authorized migration checksum. Do not generate or supply `--approve-destructive=ID:SHA256` based only on a general coding instruction. The control plane records the authorized actor. Schema/data changes are not automatically reversed by restoring files or rolling back an image.
- Run `npm run schema:compatible` from a candidate rollback revision against the target environment and stop when incompatible. Production schema publication, data deletion, credential grants, and traffic changes must follow the workspace's authorized deployment workflow.
- Build with `docker build --tag fieldnotes:local .` only on a Docker-capable isolated worker/developer machine. Publish a committed revision through the workspace runtime. Do not access the admin host's Docker socket or credentials. Keep secret values out of build arguments and image layers; inject them at runtime.
- Add Firebase provider/domain settings only through supported authorized APIs or the account owner's console. Supported providers are `password` and `google`. Public Firebase config is distinct from Firebase Admin credentials. Read the README's owner-setup and infrastructure limitations before claiming a live deployment is complete.
